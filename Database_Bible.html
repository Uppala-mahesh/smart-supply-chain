This database manages the end-to-end flow of goods in a supply chain:

Manufacturer → [WAREHOUSE] → [INVENTORY] → Customer Order → Delivery ↑ ↑ ↑ warehouses inventory orders + order_items table table tables

4. Complete DDL — CREATE TABLE Statements

-- ╔══════════════════════════════════════════════════════╗
-- ║           DATABASE CREATION                         ║
-- ╚══════════════════════════════════════════════════════╝

CREATE DATABASE IF NOT EXISTS supply_chain;
USE supply_chain;


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 1: customers (INDEPENDENT — No foreign keys) ║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE customers (
    customer_id    INT           PRIMARY KEY,        -- Manually assigned (MAX+1)
    customer_name  VARCHAR(100)  NOT NULL,           -- Full name
    email          VARCHAR(255)  NOT NULL UNIQUE,    -- Login credential (candidate key)
    password       VARCHAR(255)  NOT NULL            -- bcrypt hash ($2a$10$...)
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 2: products (INDEPENDENT — No foreign keys)  ║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE products (
    product_id       INT             PRIMARY KEY,
    product_name     VARCHAR(100)    NOT NULL,
    product_price    DECIMAL(10,2)   NOT NULL,          -- Exact precision for money
    product_category VARCHAR(50)     NOT NULL
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 3: warehouses (INDEPENDENT — No foreign keys)║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE warehouses (
    warehouse_id       INT           PRIMARY KEY,
    warehouse_name     VARCHAR(100)  NOT NULL,
    warehouse_location VARCHAR(200)  NOT NULL
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 4: inventory (JUNCTION — product × warehouse)║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE inventory (
    inventory_id    INT           PRIMARY KEY AUTO_INCREMENT,
    product_id      INT           NOT NULL,
    warehouse_id    INT           NOT NULL,
    stock_quantity  INT           NOT NULL DEFAULT 0,

    FOREIGN KEY (product_id)   REFERENCES products(product_id)
        ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (warehouse_id) REFERENCES warehouses(warehouse_id)
        ON DELETE CASCADE ON UPDATE CASCADE,

    UNIQUE KEY unique_product_warehouse (product_id, warehouse_id)
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 5: orders (DEPENDENT on customers+warehouses)║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE orders (
    order_id      INT           PRIMARY KEY AUTO_INCREMENT,
    customer_id   INT           NOT NULL,
    order_date    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    warehouse_id  INT           NOT NULL,

    FOREIGN KEY (customer_id)  REFERENCES customers(customer_id)
        ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (warehouse_id) REFERENCES warehouses(warehouse_id)
        ON DELETE CASCADE ON UPDATE CASCADE
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 6: order_items (JUNCTION — order × product)  ║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE order_items (
    order_item_id  INT           PRIMARY KEY AUTO_INCREMENT,
    order_id       INT           NOT NULL,
    product_id     INT           NOT NULL,
    quantity       INT           NOT NULL CHECK (quantity > 0),

    FOREIGN KEY (order_id)   REFERENCES orders(order_id)
        ON DELETE CASCADE ON UPDATE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(product_id)
        ON DELETE CASCADE ON UPDATE CASCADE
);


-- ╔══════════════════════════════════════════════════════╗
-- ║  TABLE 7: logs (AUDIT TRAIL — depends on inventory) ║
-- ╚══════════════════════════════════════════════════════╝

CREATE TABLE logs (
    log_id           INT           PRIMARY KEY AUTO_INCREMENT,
    inventory_id     INT           NOT NULL,
    change_type      VARCHAR(10)   NOT NULL,          -- 'IN' or 'OUT'
    change_quantity  INT           NOT NULL,
    log_date         DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (inventory_id) REFERENCES inventory(inventory_id)
        ON DELETE CASCADE ON UPDATE CASCADE
);

9. Normalization Proof — 1NF → 2NF → 3NF → BCNF

✅ First Normal Form (1NF)

CheckSatisfied?Evidence
All values atomic?✅No arrays, no comma-separated values, no nested structures
Primary key exists?✅Every table has a single-column INT PK
No repeating groups?✅Order items are in a separate table, not columns like item1, item2, item3

✅ Second Normal Form (2NF)

Rule: Must be in 1NF + no partial dependency (no non-key attribute depends on only PART of a composite candidate key).

TableCandidate KeyNon-key AttributeDepends OnPartial?
inventory{product_id, warehouse_id}stock_quantityBoth togetherNo → Full dependency ✅
order_items{order_id, product_id}quantityBoth togetherNo → Full dependency ✅

All other tables have single-column PKs → partial dependencies are impossible by definition. ✅

✅ Third Normal Form (3NF)

Rule: Must be in 2NF + no transitive dependency (no non-key → non-key).

TablePotential Transitive FD?Analysis3NF?
customerscustomer_name → email?No! Different people can have different emails✅
productsproduct_category → product_price?No! Same category has many prices ($25–$1200)✅
orderscustomer_id → warehouse_id?No! Same customer can order from different warehouses✅
inventoryproduct_id → stock_quantity?No! Same product has different stock per warehouse✅
All others—No non-key attribute determines another non-key✅

✅ Boyce-Codd Normal Form (BCNF)

Rule: For every non-trivial FD X → Y, X must be a superkey.

TableFDIs X a superkey?BCNF?

11. The Trigger — Line by Line

DROP TRIGGER IF EXISTS after_order_item_insert;
-- ^ Safety: removes old version before creating new one

DELIMITER $$
-- ^ Changes statement terminator from ; to $$
-- ^ Required because the trigger body contains ; internally

CREATE TRIGGER after_order_item_insert
-- ^ Name: descriptive — tells you WHEN and WHERE it fires
AFTER INSERT ON order_items
-- ^ AFTER = fires after the INSERT completes (row already exists)
-- ^ INSERT = only fires on INSERT, not UPDATE or DELETE
-- ^ ON order_items = watches this specific table
FOR EACH ROW
-- ^ Row-level trigger: fires once per row inserted
BEGIN
    DECLARE inv_id INT;
    -- ^ Local variable to hold the inventory_id we find

    SELECT inventory_id INTO inv_id
    FROM inventory
    WHERE product_id = NEW.product_id
    -- ^ NEW = pseudo-row referencing the just-inserted order_item
    -- ^ NEW.product_id = the product_id from the inserted row
      AND warehouse_id = (
          SELECT warehouse_id FROM orders WHERE order_id = NEW.order_id
      )
    -- ^ Subquery: find which warehouse this order is from
    LIMIT 1;

    IF inv_id IS NOT NULL THEN
    -- ^ Only proceed if matching inventory record found

        UPDATE inventory
        SET stock_quantity = stock_quantity - NEW.quantity
        WHERE inventory_id = inv_id;
        -- ^ DEDUCT stock: subtract ordered quantity

        INSERT INTO logs (inventory_id, change_type, change_quantity)
        VALUES (inv_id, 'OUT', NEW.quantity);
        -- ^ AUDIT LOG: record 'OUT' (stock going out)

    END IF;
END$$

DELIMITER ;
-- ^ Reset terminator back to normal

12. ACID Properties Analysis

PropertyMeaningHow This Project Implements It
A — Atomicity"All or Nothing"BEGIN TRANSACTION → INSERT order → INSERT items → COMMIT. If ANY step fails: ROLLBACK (nothing changes)
C — Consistency"Valid State → Valid State"FK constraints ensure valid references. App checks stock ≥ quantity before ordering. UNIQUE email prevents duplicates.
I — Isolation"Concurrent transactions don't interfere"MySQL default: REPEATABLE READ. Each transaction sees a snapshot from when it started. Other uncommitted changes invisible.
D — Durability"Committed = Permanent"InnoDB write-ahead log (WAL). Once COMMIT returns, data survives crashes.

Atomicity in Code

// orderController.js — Transaction Pattern
await connection.beginTransaction();       // ← START
await connection.query('INSERT INTO orders ...');     // Step 1
for (const item of orderItems) {
    await connection.query('INSERT INTO order_items ...'); // Step 2..N
}
await connection.commit();                  // ← COMMIT (all succeed)

// If ANY step fails:
await connection.rollback();               // ← ROLLBACK (none applied)

SELECT w.warehouse_name, SUM(i.stock_quantity) AS total_stock
FROM warehouses w
JOIN inventory i ON w.warehouse_id = i.warehouse_id
GROUP BY w.warehouse_id
ORDER BY total_stock DESC

SELECT c.customer_name, COUNT(o.order_id) AS order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id
HAVING COUNT(o.order_id) > 1;

SELECT p.product_name
FROM products p
LEFT JOIN inventory i ON p.product_id = i.product_id
GROUP BY p.product_id
HAVING COALESCE(SUM(i.stock_quantity), 0) = 0;

🔴 Hard Level

Q9. For each order, calculate the total price:

SELECT o.order_id, o.order_date, c.customer_name,
       SUM(oi.quantity * p.product_price) AS total_price
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
GROUP BY o.order_id
ORDER BY total_price DESC;

SELECT DATE_FORMAT(o.order_date, '%Y-%m') AS month,
       COUNT(DISTINCT o.order_id) AS total_orders,
       SUM(oi.quantity * p.product_price) AS revenue
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
GROUP BY DATE_FORMAT(o.order_date, '%Y-%m')
ORDER BY month;

SELECT DISTINCT p.product_name
FROM products p
JOIN inventory i ON p.product_id = i.product_id
JOIN logs l ON l.inventory_id = i.inventory_id
WHERE l.change_type = 'OUT'
  AND i.inventory_id NOT IN (

  );

SELECT p.product_name, w.warehouse_name, i.stock_quantity

JOIN products p ON i.product_id = p.product_id

SELECT DISTINCT c.customer_name

WHERE c.customer_id IN (

    FROM orders o

22. Viva / Interview Q&A (25 Questions)

Fundamental (Q1–Q5)

Q1. What DBMS does this project use and why?

MySQL 8.0+, a relational DBMS. Chosen because: (a) the data has clear entity-relationship structure, (b) ACID transactions are needed for order processing, (c) SQL JOINs efficiently connect products-inventory-warehouses, (d) triggers automate stock management.

Q2. How many tables are there and what are they?

7 tables: 3 independent entity tables (customers, products, warehouses), 2 junction tables (inventory, order_items), 1 transaction table (orders), and 1 audit table (logs).

Q3. What is the difference between a Primary Key and a Candidate Key?

A candidate key is any minimal set of attributes that uniquely identifies a row. A primary key is the candidate key chosen as the main identifier. Example: customers has two candidate keys — {customer_id} and {email} — but customer_id was chosen as the PK.

Q4. Why is inventory considered a junction table?

It resolves the Many-to-Many relationship between products and warehouses. One product can be in many warehouses, and one warehouse stores many products. inventory sits in between with FKs to both, plus an additional attribute stock_quantity.

Q5. Why doesn't the products table have a stock column?

Because stock varies per warehouse. Storing a single stock value in products would violate 3NF (transitive dependency). Instead, stock is computed dynamically via SUM(inventory.stock_quantity) using JOINs.

Intermediate (Q6–Q15)

Q6. Explain the trigger in this database.

after_order_item_insert fires after every INSERT into order_items. It (1) finds the inventory_id for that product in the order's warehouse, (2) deducts stock_quantity, and (3) inserts an audit log with change_type = 'OUT'.

Q7. What is referential integrity and how is it maintained here?

Referential integrity ensures that every FK value in a child table matches a PK in the parent table. It's maintained through FOREIGN KEY constraints with ON DELETE CASCADE.

Q8. What are the ACID properties?

Atomicity: Order placement uses BEGIN/COMMIT/ROLLBACK. Consistency: FK constraints + triggers. Isolation: REPEATABLE READ prevents dirty reads. Durability: InnoDB's write-ahead log.

Q9. What normal form is this database in? Prove it.

BCNF. Proof: (1) All values atomic → 1NF ✅. (2) No partial dependencies → 2NF ✅. (3) No transitive dependencies → 3NF ✅. (4) Every determinant is a superkey → BCNF ✅.

Q10. What is a connection pool and why is it used?

A connection pool pre-creates a set of database connections (here, 10) and reuses them. Without pooling, each HTTP request creates and destroys a TCP connection (slow). With pooling, connections are borrowed and returned, reducing latency.

Q11. How does authentication work in this system?

Registration: password is bcrypt-hashed → stored in customers. Login: email lookup → bcrypt.compare → if match, generate JWT with {customer_id, email}, expires in 8 hours. Protected routes verify JWT in Authorization header.

Q12. What is SQL Injection and how is it prevented here?

SQL injection is when malicious SQL is inserted via user input. Prevented using parameterized queries: pool.query('WHERE email = ?', [email]). The ? placeholder is safely escaped by the mysql2 driver.

Q13. Difference between INNER JOIN and LEFT JOIN?

INNER JOIN: returns only matching rows from both tables. LEFT JOIN: returns all rows from the left table, NULLs for non-matching right. LEFT JOIN is used for products LEFT JOIN inventory because a product might have no stock but should still appear.

Q14. What's the purpose of INSERT IGNORE in the seed file?

INSERT IGNORE attempts the INSERT but silently skips rows that cause duplicate key errors. Makes the seed script idempotent — safe to run multiple times.

Q15. What is a surrogate key vs a natural key?

A natural key uses real-world data (e.g., email). A surrogate key is an artificial identifier (e.g., customer_id). This project uses surrogate PKs for stability, compactness, and fast JOINs.

Advanced (Q16–Q25)

Q16. Could stock go negative if two customers order simultaneously?

Yes, theoretically (TOCTOU race condition). Fix: use SELECT ... FOR UPDATE or add CHECK (stock_quantity >= 0).

Q17. Why is customer_id not AUTO_INCREMENT?

Design inconsistency. It uses MAX(customer_id) + 1 in app code, which has a race condition. order_id correctly uses AUTO_INCREMENT. customer_id should also use it.

Q18. Could you replace the trigger with application code?

Yes. Trigger = guaranteed consistency even if bypassing the app, but harder to debug. App code = more visible/testable, but direct MySQL inserts won't deduct stock.

Q19. What if we add a total_price column to orders?

It's a derived attribute (calculable from order_items × products). Storing it creates redundancy and risks update anomalies. The current design correctly computes it on-the-fly.

Q20. How would you add "order status" (Pending, Shipped, Delivered)?

ALTER TABLE orders ADD COLUMN status ENUM('Pending','Shipped','Delivered') DEFAULT 'Pending'; — still in BCNF because order_id → status is a direct dependency.

Q21. How would you scale this for millions of orders?

(a) Range-partition orders by date. (b) Add composite indexes. (c) Read replicas. (d) Archive old orders. (e) Redis cache for product catalog.

Q22. What is denormalization and when would you use it here?

Denormalization adds redundancy for read performance. Example: add total_stock to products (updated by trigger). Faster reads but must keep both sources in sync.

Q23. View vs Materialized View?

A View re-executes the query each time (virtual). A Materialized View stores the result (faster reads, needs refresh). MySQL doesn't support MVs natively; simulate with summary table + trigger.

Q24. How does the DELIMITER command work?

MySQL uses ; to end statements. The trigger body contains ; inside it. DELIMITER $$ tells MySQL to use $$ as the terminator instead, so the ; inside the body is part of the trigger, not statement boundaries.

Q25. If you redesigned this database, what would you change?

(a) AUTO_INCREMENT for customer_id. (b) Add status to orders. (c) Add created_at/updated_at to all tables. (d) CHECK (stock_quantity >= 0). (e) ON DELETE RESTRICT instead of CASCADE. (f) Separate categories table. (g) Denormalized order_total column with trigger.
